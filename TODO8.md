## Corrections carried from the PRD 8 critique — read this before §1

The critique found two things in PRD 8's first draft that were not buildable as written (both fixed in the PRD itself, and reflected in every relevant item below — flagged here so the contradiction between the *first draft* and *this checklist* is visible, not silently absorbed):

1. **The first draft proposed a new state-machine state, `AWAITING_CAPTURE_RESPONSE`, entered via `VERIFYING → AWAITING_CAPTURE_RESPONSE`, driven by a separate `claim_capture_if_warranted()` call made *after* `take_turn()` returns.** This is unreachable: `commit_and_reveal_to_peer` (which `take_turn()` calls into) already unconditionally transitions to `WAITING_FOR_OPPONENT` before returning — `VERIFYING` is gone by the time such a call would run. **Corrected:** no new state at all. The capture-claim send-and-await lives *inside* `commit_and_reveal_to_peer`, in the existing `AWAITING_REVEAL` window, sibling to the barrier-declaration block already there — reusing that state's already-legal `TECHNICAL_LOSS` edge. §2, below, builds this. `planner/state_machine.py` is **not touched** by this layer at all — if any task below is drafted assuming otherwise, that task is wrong, not this note.
2. **The first draft's `claims_capture()` signature took `target_pos` as a parameter but never said who captures the correct value or when.** `take_turn()` overwrites `self.game_state.target_pos` with the *next* turn's belief before `commit_and_reveal_to_peer` is ever called — a capture check running inside `commit_and_reveal_to_peer` (per fix #1) would silently compare against the wrong turn's belief unless the correct, pre-overwrite value is captured earlier and threaded through explicitly. **Corrected:** §1/§2 below capture it in `take_turn()` immediately after the move is applied, before the overwrite, and pass it into `commit_and_reveal_to_peer` as a new `believed_thief_pos` parameter.

Two smaller gaps the critique also found, both folded into §3 rather than called out as their own sections: `self.log_path` and `self.league_ledger` don't exist on `Orchestrator` today, despite `report_game()`'s own design already assuming both.

## Found only by actually running this layer, not anticipated by the critique or the design pass

Neither of these was visible from reading the code — both surfaced only once the real tests actually ran, matching this project's own standing "found via reproduction, not review alone" discipline.

1. **`asyncio.Event.set()` is not thread-safe across event loops — a real, reproducible hang, not a theoretical concern.** The claiming side awaits the capture-response event inside its own `asyncio.run(...)` call (one event loop); the response arrives via this side's own MCP *server*, which runs in a genuinely separate OS thread with its own event loop (`run_as_server`, every bilateral test in this repo). Calling `.set()` directly from the server's thread never wakes a waiter parked in a different loop — confirmed by running `test_a_wrong_belief_gets_denied_and_the_game_continues_normally` under an explicit `timeout 30` and watching it actually hang. Fixed in `orchestrator_capture.py`: the claiming side records which loop it's waiting on (`self._capture_response_loop`), and `_on_capture_response_received` schedules `.set()` onto that exact loop via `call_soon_threadsafe` — the only thread-safe way to signal across loops.
2. **A pre-existing, unrelated test — `test_step_index_agreement.py`'s 12-round lockstep test — started hanging for the full 30-second deadline and then failing.** Root cause: over enough real, adaptively-moving rounds, a `CopBrain` peer's own move can legitimately land on its own belief target (that's the point of the strategy) — triggering a genuine capture claim. The *other* side, also a cop instance (rule 1/2: this repo can never run a thief brain), never answers one by design (Design Question 3) — so the claiming side hangs the full deadline before reaching `TECHNICAL_LOSS`, breaking a test that was never about captures at all. This is a structural consequence of rule 1/2's own test-harness limitation, not a bug in the capture logic — every two-real-`Orchestrator` test with enough adaptively-decided rounds is theoretically at risk; a targeted search of the existing suite found this to be the only one actually affected (the one other multi-call test in `test_orchestrator_take_turn.py` uses fixed, non-converging positions). Fixed by disabling capture detection for the duration of that one test (`monkeypatch.setattr(cop.orchestrator_capture, "claims_capture", lambda *a, **kw: None)`) — the test was never exercising capture behavior, so this narrows scope rather than weakening anything.
