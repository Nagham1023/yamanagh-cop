# PRD 5 — Cloud Exposure and Tunneling

Status: **Built, verification in progress.** Built per `TODO5.md`'s §0–§8 checklist; see "Built & verified" below for what actually landed, including one real design gap found and fixed via sanity-check sabotage after the original draft.

Read the book directly for this layer (`police_thief_p2p.pdf`, ch. 2.4–2.4.2 "Tunneling and Environment Separation" / "Why is a Tunnel Needed? NAT Traversal" / "Complete Separation of Working Environments"), not just `PLAN.md`'s paraphrase — the PRD 4 correction was a direct lesson that the book's own chapters carry detail worth reading first-hand. Two things came out of that reading that aren't in `PLAN.md`'s terse PRD 5 entry and materially shape this document: the book's own "what if reality changes" analysis explicitly frames a dropped tunnel as a **turn-blocking deadlock risk**, which is exactly why rule 6/7 hardening is listed alongside rule 10 rather than being a separate concern; and ch. 2.4.2's "complete separation of working environments" text is about *local development* discipline (a team building both cop and thief on one machine) rather than anything new for a repo that, per this project's own rule 1/2, can never hold a thief brain at all — it's cited here as confirmation that our existing per-repo separation already satisfies the *stronger* form of what that section asks for, not as a new build item.

This is a pure infrastructure layer: no game logic, no state-machine change, no new config field. `PLAN.md` §5's own explicitly-out-of-scope lines for PRDs 1–4 all name "ngrok/tunneling (PRD 5)" — this is the layer that debt was pointing at.

## Build

- **`tools/tunnel.py`** (new module) — `start_tunnel(port: int) -> Tunnel` launches `ngrok http <port>` as a subprocess (`subprocess.Popen`, same pattern this repo already uses for spawning real OS-process peers), then polls ngrok's own local admin API (`http://127.0.0.1:4040/api/tunnels`, plain `httpx.get` — already a dependency, no new one needed) until the public HTTPS URL is available; returns a small `Tunnel` dataclass holding the process handle and the resolved `public_url`. `stop_tunnel(tunnel: Tunnel) -> None` terminates it. ngrok chosen over Localtonet as the concrete implementation (the book permits either; building both would be undocumented scope creep for zero milestone benefit) — documented here, not silently narrowed.
- **Caller-IP capture** — `tools/mcp_server.py`'s `receive_hint` gains a small helper reading the caller's real IP: prefer the `X-Forwarded-For` header (what a tunnel actually inserts — the raw ASGI `request.client.host` is always `127.0.0.1` when traffic arrives via a local tunnel client forwarding to localhost, so reading that instead would silently defeat the milestone's own verification method), falling back to `request.client.host` when no such header is present (direct localhost/LAN testing, no tunnel in front). Must degrade gracefully (no crash, no hang) when there is no active HTTP request at all — every existing unit test calls tools through FastMCP's in-process `Client(mcp)` transport, which has no real HTTP layer to read a header from.
- **`on_receive`'s callback signature grows to carry that IP** — `Callable[[str | None], None]`, still fired on every successful `receive_hint` call. `Orchestrator` replaces its direct `on_receive=self.watchdog.heartbeat` wiring with a new bound method that does both jobs together (heartbeat *and* `trace.log("connection_received", ip=...)`) — a connection event and a "who connected" event are the same occurrence, not two.
- **`Orchestrator.run_as_server` gains an opt-in `use_tunnel: bool = False` parameter.** When `True`, wraps the existing serve loop with `start_tunnel`/`stop_tunnel`, logging the resolved public URL (`trace.log("tunnel_started", public_url=...)`) before blocking on `self.server.run(...)`, and stopping the tunnel in a `finally`. Deliberately opt-in and additive: every existing test constructs and runs an `Orchestrator` with no tunnel involved at all, and none of that behaviour may change. Budget the 150-line house cap before writing this — `orchestrator.py` is already the tightest file in the repo at 145 lines; if this pushes it over, extract into `orchestrator_turn.py` (has more headroom) rather than force it in.
- **Host binding.** `host`'s type changes to `str | None = None`, resolved inside the method: `host = host or ("0.0.0.0" if use_tunnel else "127.0.0.1")`. The book's own minimal FastMCP example (ch. 2.3, page 28) binds `host="0.0.0.0"` with the explicit comment "so a tunnel can expose it publicly" — every existing call site either already passes `host="127.0.0.1"` explicitly or relies on the default with `use_tunnel` absent, so this is additive, not a behaviour change for anything already built. See Design Question 5.
- **`.claude/agents/adversary.md`** — a new Claude Code subagent, named directly in `PLAN.md`'s own repository layout (§7) as "hostile peer simulator, from PRD 5," sitting alongside the already-built `rule-auditor.md`. `PLAN.md` names it but never elaborates further — its job, inferred from where it's introduced (this layer, right next to "hardening of rules 6/7 under real network conditions") and from the milestone's own "also verify" line, is to automate exactly the kind of hostile-network poking a human would otherwise have to do by hand: spin up a real peer, then deliberately misbehave against it (drop the connection mid-turn, delay a response past the deadline, send a malformed payload) and report whether rule 6/7 held — a real crash/hang is a finding, not something the subagent fixes (same read-only-verdict posture as `rule-auditor.md`, `Read`/`Bash` tools only, no `Edit`/`Write`).

## Explicitly out of scope

- Any change to game logic, the state machine, or turn structure — this layer is purely "the same MCP infrastructure from chapter 2, now crossing the network" (the book's own framing for this step, ch. 10.3.5). `PeerStateMachine` gains no new states; `TECHNICAL_LOSS` stays exactly as terminal as PRD 2 built it (see Design Question 1 below for why "handle reconnection" doesn't change that).
- Table 19's Gatekeeper pattern (`retries`, `retry_delay_seconds`, `requests_per_minute`, `parallel_requests`, `queue_depth` — Table 19 items #1–5) — explicitly PRD 7's `policy/gatekeeper.py`, per every prior PRD's own accounting of that table. This layer continues using only the two Table 19 fields already wired since PRD 2 (`response_timeout_seconds` item #6, `watchdog_threshold_seconds` item #7) — read that closely: rule 6/7's own numeric parameters live in the *same* Table 19 as the Gatekeeper's, which is exactly why "hardening 6/7" must not be read as license to start wiring the rest of that table early.
- Commit-Reveal, nonces, hashing, Step-0 — PRD 6.
- Automating the exchange of dynamic tunnel URLs between the two teams. ngrok's free tier issues a new URL on every restart, so it cannot be baked into the shared, cryptographically-locked config (which must stay byte-identical and static). `take_turn(peer_url)` already accepts an arbitrary URL string — a tunnel URL works with zero code change on the *sending* side. How the operator learns the opponent's current URL (email, a shared doc, whatever a real match's pre-game handshake looks like) is a human, operational step, not something this layer's code automates.
- Localtonet as a second, parallel implementation — ngrok only, documented as a deliberate choice above.
- GUI, Replay app, Gmail reporting — PRD 7.

## Milestone

An agent on a genuinely remote machine — a different network, not a second process on the same laptop — connects through a real ngrok tunnel and plays a full round against the local agent. Confirmed by reading the opponent's IP out of the `connection_received` trace log entries: it must not be `127.0.0.1` or a LAN-local (`192.168.x.x` / `10.x.x.x`) address. Requires a human with a real ngrok account and a second machine (or a teammate on a different network) to actually run — same "watched end-to-end by a human" discipline as every prior layer's milestone, since no CI environment can honestly claim to be "a genuinely different network."

**Also verify:** a mid-game tunnel drop produces a clean technical loss with an intact log, not a hang and not a crash.

## Design questions answered here (not left for code-time guessing)

**1. What does "handle... reconnection" (`PLAN.md`'s Build line) actually mean, given rule 6 already exists and Table 19's retry machinery is explicitly PRD 7's?** Not a new retry-with-backoff subsystem in this repo's code. Read directly, ch. 8.4.1 defines the Deadline Tracker pattern itself in exactly these terms: "for every request over MCP with an expiry deadline, once that deadline passes, the system must either perform a Retry, or declare a controlled technical loss and close the turn cleanly." That "either/or" is the book's own architecture presenting immediate technical loss as one of two fully valid responses to a missed deadline — not a partial implementation of a mandatory retry requirement. PRD 2's existing choice (immediate technical loss, no retry) is fully book-sanctioned on this direct textual basis, reinforced by Table 19 grouping `response_timeout_seconds`/`watchdog_threshold_seconds` (items #6/#7, already wired since PRD 2) in the *same* table as `retries`/`retry_delay_seconds` (items #3/#4, PRD 7's Gatekeeper) — evidence the book treats them as one coherent mechanism, not two independent ones to split apart early. Building a second, parallel retry system here — before the Gatekeeper exists to own it — would repeat exactly the kind of premature scaffolding this project has already found dangerous once (rule 27's PRD 2 carve-out). "Reconnection" here means two things, both already true or already testable without new production logic: ngrok/Localtonet handle their own transport-level reconnection beneath the tunnel abstraction (not this repo's concern); and a **transient** hiccup within the existing, generous `response_timeout_seconds` (30s, Table 19 #6) budget must not spuriously trip technical loss — verified by a new test with a modest, realistic delay well under that budget, contrasted with the existing tests that deliberately *shorten* the deadline to force a timeout. A **genuine** drop still reaches `TECHNICAL_LOSS` on the very next attempt, exactly as PRD 2 built it. `PeerStateMachine` gains no new states.

*(Also confirmed while reading ch. 8.4.2: the book's illustrative `watchdog_check(last_heartbeat, timeout_sec=180)` code example uses `180` as a placeholder, not `60` — the actual locked `watchdog_threshold_seconds` value. Same "illustrative number, not an overriding one" pattern `CLAUDE.md` already documents for the Gatekeeper's own example numbers, not a new contradiction.)*

**2. Why extend `on_receive` rather than add a third argument to `on_hint`, or a wholly new callback?** `on_hint`'s payload has already grown once in this project's history (`text` → `text, scent_report`, PRD 4 Revision 1) and both of those are about the *content* of what the peer said. The caller's IP isn't content — it's a fact about the *connection itself*, the same category `on_receive`'s existing single job (the watchdog heartbeat) already belongs to. A third callback would mean a third place `build_server` has to remember to wire and a third place tests have to construct — extending the connection-shaped callback keeps the two categories (connection vs. content) cleanly separated instead of collapsing everything into one payload that keeps growing.

**3. Why prefer `X-Forwarded-For` over the raw ASGI `request.client.host`, and what happens with no tunnel in front at all?** Read directly from `fastmcp.server.dependencies`: `get_http_request()` returns the Starlette `Request`; its `.client.host` is the IP of whoever opened the raw TCP connection to this process — which, once a tunnel is in front, is always the tunnel's own local forwarding client (`127.0.0.1`), never the real remote caller. `X-Forwarded-For` is the header a tunnel actually inserts with the true origin address. Falling back to `request.client.host` when that header is absent keeps direct localhost/LAN testing (no tunnel) working exactly as it does today — the milestone's own verification method (grep the log for a non-loopback, non-LAN address) is precisely what would silently break if this were built the other way around.

**4. Should tunnel-starting be automatic inside `Orchestrator.__init__`, given rule 10 says it's mandatory for a real match?** No — every one of the 218 existing tests constructs an `Orchestrator` and expects pure localhost behaviour with zero external process spawned. Rule 10 governs how a *real, counted match* must be run, not how every test fixture must behave; ch. 2.4's own text is explicit that localhost is legitimate "in the early coding stages." `use_tunnel` defaults to `False` and stays opt-in on `run_as_server` specifically so this layer is purely additive — nothing already built changes behaviour unless a caller deliberately asks for it.

**5. Why bind `0.0.0.0` only when `use_tunnel=True`, rather than changing the default for everyone?** The book's own minimal FastMCP example (ch. 2.3, page 28) ends the exact same "expose a tool over the network" walkthrough this repo's `tools/mcp_server.py` is built from with `mcp.run(transport="http", host="0.0.0.0", port=8000)`, commented explicitly: "Bind the server so a tunnel can expose it publicly." This is not a PRD 2 regression to go fix retroactively — PRD 2/3/4 were correctly, deliberately scoped to localhost-only (PRD 4's own "Builds on" line says so), and `127.0.0.1` was the right choice for that scope; it's specifically *this* layer, where the server first needs to be reachable from outside the loopback interface at all, that the book's guidance becomes load-bearing rather than just a stylistic preference. Binding `0.0.0.0` unconditionally for every caller (including the 218 existing tests) would widen every test's ephemeral server to the whole LAN for no benefit; resolving it only when `use_tunnel=True` keeps the change scoped to exactly the case the book's own comment describes.

- `start_tunnel` fails loudly and clearly when the `ngrok` binary isn't on `PATH` at all, rather than hanging on the admin-API poll
- A caller's `X-Forwarded-For` header, when present, is what ends up in the `connection_received` trace log — not the raw loopback address — proven over a real HTTP round-trip (not the in-process test transport, which has no headers to read)

- `run_as_server(use_tunnel=True)` resolves `host` to `0.0.0.0`; `run_as_server()`/`run_as_server(use_tunnel=False)` still resolves to `127.0.0.1`, unchanged from today

- A connection that succeeded once and then dies before the *next* attempt still reaches `TECHNICAL_LOSS` cleanly, with an intact log — the "was working, then the tunnel dropped" shape, not just "never worked at all" (PRD 2's existing dead-port test)

## Built & verified

Everything in "Build" landed per `TODO5.md`'s §0–§8. `orchestrator.py` blew the 150-line cap a second time once the host-binding/tunnel-lifecycle logic landed (170 lines) — extracted into a new `orchestrator_server.py` (`ServerLifecycleMixin`, 55 lines), a cleaner split than the PRD's own guess of reusing `orchestrator_turn.py`: server *lifecycle* (watchdog poll loop, `run_as_server`, tunnel start/stop) is a genuinely different concern from brain-driven *turn-taking*, and conflating them into one file for cap-avoidance alone would have been the wrong trade.

**One real design gap found via sanity-check sabotage, not anticipated in the draft.** The first attempt to sabotage `_caller_ip()`'s header-preference order (swap it to check `request.client.host` before `X-Forwarded-For`) didn't make the real-HTTP test fail — both orderings produced the same answer. Investigating why surfaced a genuine fact about the deployment that the original design hadn't accounted for: uvicorn's own `ProxyHeadersMiddleware` (enabled by default, `trusted_hosts="127.0.0.1"`) already rewrites `request.client.host` to match `X-Forwarded-For` for any connection originating from `127.0.0.1` — which is *every* connection in this test suite, and every real ngrok connection too (the tunnel's own local forwarding agent always connects via loopback). This means `_caller_ip()`'s explicit header-first preference is redundant with that middleware in the current deployment, not conflicting with it — but relying on an uvicorn implementation default the code never asserts would be fragile (a different ASGI server, or a reconfigured `forwarded_allow_ips`, would silently break it). Added a second, isolated test (`test_caller_ip_prefers_the_x_forwarded_for_header_over_request_client_host`) that monkeypatches `get_http_headers`/`get_http_request` directly rather than going through real HTTP, specifically so the preference order is provably this function's own logic — confirmed it genuinely catches the swapped-order sabotage, then reverted.

`.claude/agents/adversary.md` could not be invoked as a registered subagent this session (new `.claude/agents/*.md` files aren't picked up until a fresh session) — its procedure was instead run live, once, via a general-purpose agent instructed to follow the file's own steps verbatim, against a real spawned `_server_process.py` peer. All three scenarios (drop mid-turn, delay past the deadline, malformed payload) HELD: a dead peer after one successful exchange reached `TECHNICAL_LOSS` in under 200ms; a silent peer's deadline expiry landed within ~30ms of the configured `response_timeout_seconds` at both a shortened (5s) and the real, unshortened (30s) value; malformed payloads were rejected cleanly (either `ToolError` for shape violations, or a soft `accepted: false` for the over-limit-string case — both acceptable, neither crashed or hung) with the trace log intact throughout. That run's one finding — the malformed-payload scenario's wording only named `ToolError`, not the softer value-level rejection the word-limit case actually produces — was folded back into `adversary.md` itself.

§7's real milestone (a genuinely remote machine connecting through an actual ngrok tunnel) was **not** run — it needs a human with a real ngrok account and a second network, neither of which this session has. Documented as a pending, human-run step; not claimed as done.
