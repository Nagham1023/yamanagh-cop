# PRD 6 — Security and Cryptography

Status: **Not built. Design frozen here first**, same PRD → TODO → execute discipline every prior layer used — this is the largest, most fatal-rule-dense layer in the project (five of the fourteen zeroes live here: rules 11/12, 15/16, 17/18/19, 21/22, 23's audit half), so nothing below gets guessed at code time.

This is the layer that turns "we built an honest peer" into "we built a peer that *cannot get away with* being dishonest." Every prior PRD's Intent flag, scent map, and hint text has been generated honestly by construction — nothing has ever cryptographically forced it to be. PRD 6 is where that changes: Commit-Reveal over SHA-256, Step-0's hardware/code declaration, and the end-of-game mutual audit that makes a lie provable, not just discouraged.

`PRD-6-prep-commit-payload-spec.md` (built ahead of schedule, before this doc) already froze `canonical_state_bytes()`'s field list — this PRD builds on that, doesn't redo it, and extends it once (Design Question 5 below).

## Build

- **`src/cop/integrity/nonce.py`** — `generate_nonce() -> str`, `secrets.token_hex(16)` per rule 18/`PLAN.md`'s own mandate. One function, exists so nothing anywhere else in `integrity/` reaches for `random`/hand-rolls hex generation.
- **`src/cop/integrity/commit_reveal.py`** — the book's own `commit()`/`verify()` pair (ch. 5.3.1, p.53's worked code), built on top of `commit_payload.py::canonical_state_bytes` for the `State` component rather than re-deriving it. `commit(state_bytes, move, intent, nonce, hint_text, step, role) -> (h_commit: str, nonce: str)`; `verify(...) -> bool` using `secrets.compare_digest`, never `==`.
- **`src/cop/integrity/step0.py`** — the pre-game declaration: hardware spec (OS, CPU core count, RAM, GPU/VRAM presence), LLM model name, code git-commit hash (rule 53), group name, `sub_game_number` — ch. 5.5's own field list, exactly — plus one field the book doesn't ask for, config SHA-256, added here to close rule 11's enforcement gap (Design Question 3 labels this explicitly as this repo's own extension) — all cryptographically signed via canonical JSON.
- **`src/cop/integrity/audit.py`** — the end-of-game mutual audit: replay every turn's revealed `(State, Move, Intent, Nonce, hint_text, step, role)`, recompute `Hcommit`, compare against what was actually broadcast at commit time (`secrets.compare_digest`), fail *any* mismatch (rule 19, no mercy). `verify_scent_map_against_commit(claimed_field, commit_hash) -> bool` lives here — the exact API `tests/unit/test_prd6_scent_audit_guard.py` already names.
- **`src/cop/integrity/capture_protocol.py`** — `claim_capture(thief_pos, cop_pos) -> CaptureClaim`, `respond_to_capture_claim(claim, true_thief_pos) -> CaptureResponse` (`.confirmed: bool`) — the exact API `tests/unit/test_prd6_missing_wire_channels_guard.py` already names. Rules 21/22: the cop's claim and the thief's response both get folded into that side's own next commit, checked like everything else at final audit — there is no separate, weaker truth mechanism for captures than for moves.
- **`src/cop/planner/state_machine.py`** — extend `TRANSITIONS` with the commit/reveal states (Design Question 4).
- **`src/cop/tools/mcp_server.py` / `mcp_client.py`** — new tools (Design Question 2 has the exact shape): `receive_commit`, `receive_reveal`, `receive_final_reveal`, `receive_barrier_declaration`, `receive_capture_claim`/`receive_capture_response`.
- **Config identity gate** — `check_config.py --identical` wired into Step-0's own pre-game checklist; config SHA-256 included in the Step-0 declaration itself as this repo's own extension, not a book-mandated field (Design Question 3).
- **Delete both guard `xfail`s** (`test_prd6_missing_wire_channels_guard.py`, `test_prd6_scent_audit_guard.py`) in the same commit that makes them pass for real — same discipline as `RULE-27-REMOVE-AT-PRD-4`.

## Milestone

A move is committed (`Hcommit` sent, nothing else), acknowledged, revealed (`Move` + hint text, nonce still hidden), and — at a separate, later "end of game" point — the nonce is finally revealed and `integrity/audit.py` recomputes `Hcommit` from the real `(State, Move, Intent, Nonce, hint_text, step, role)` and confirms it matches what was broadcast. Step-0 verifies hardware (a real declaration object, signed, containing the fields ch. 5.5 lists). A **second, adversarial** milestone, matching this project's own "a verifier that has never rejected anything is indistinguishable from a broken one" rule: deliberately tamper one field after commit, before reveal, and confirm the audit **rejects** it — not just that the honest path passes.

## Design questions answered here (not in code)

**1. Exactly what enters `Hcommit`, now that PRD 6 is real?** `PRD-6-prep-commit-payload-spec.md` already froze `State` (`own_pos`, `steps_taken`, sorted `barriers_placed`) — unchanged, not reopened. But ch. 5.3.1's own equation (`Hcommit = SHA256(State‖Move‖Intent‖Nonce)`) is explicitly *not* the whole story: p.51, read directly, says "the concatenation, in the reference implementation, is done via canonical JSON serialization... the record actually signed is richer than the four fields here, and also includes the verbal hint, the Intent classification, the step number, and the role." So the real envelope is a flat canonical-JSON object with seven top-level keys: `state`, `move`, `intent`, `nonce`, `hint_text`, `step`, `role` — `hint_text`/`step`/`role` are new, sibling to `state`, not nested inside it (State's own frozen scope is unchanged). `step` duplicates `state.steps_taken` deliberately — the book calls it out as its own component, and having it both places is free defense-in-depth against a broken `State`, not redundancy worth trimming. `role` is the literal string `"cop"` (this repo's own role, never `"thief"` — rule 1/2's process separation means this value is a compile-time constant here, not something read from anywhere).

**2. What does "Move" being revealed every turn (Figure 6, p.52) actually mean for rule 27 and for the whole partial-observability premise?** This is the tension this PRD's own intro flags, worked through in full: ch. 4.4's scent-corroboration mechanic ("thief claims 'I moved north'... scent shows south") only makes sense if the opponent doesn't already have a *proven* move history — otherwise there's nothing to corroborate, the claim would just be checkable directly. Ch. 5.3.2, read precisely: Step 3 ("Reveal: Move + Hint") happens with **the Nonce still hidden** ("`Nonce` remains hidden in this stage, to prevent reverse-engineering of the hashes before their time") — meaning nothing received at Reveal time can be cryptographically checked against the earlier `Hcommit` yet, since the nonce is the missing ingredient. **Resolution:** the `Move` revealed at Step 3 is an *unverified claim*, exactly the same trust status as the verbal hint — not proof. Only Step 4 (Final Reveal, ch. 5.3.2: "only at the end of the game are all Nonce values revealed, for the sake of a complete mutual audit") lets either side recompute `Hcommit` and discover a lie. Live gameplay stays genuinely uncertain (scent corroboration still matters turn to turn, exactly as PRD 4 built it); cryptographic proof only exists in the post-mortem. This also answers rule 27 cleanly: an ordinary `Move` is a direction string ("N"/"S"/"E"/"W"/"STAY"), never a coordinate — revealing it is not a numeric position protocol regardless of trust status. A `PlaceBarrier(target)` *is* an explicit position, but rule 15 requires disclosing exactly that; this is the "enforcement half of 15, 16" `PLAN.md`'s own PRD 6 line already names as this layer's job, not a rule 27 violation. **Worth recording as an honest, non-obvious emergent property, not silently absorbed:** once every turn's `Move` claim is being received (proven or not), a receiver tracking claims in real time can maintain a *second*, claim-based position estimate alongside the belief map — cheap to build, not required by any rule, and out of scope for this PRD's own build list, but worth flagging in the academic report as a real strategic option PRD 6 opens up.

**3. How does rule 11's "byte-for-byte identical config" actually get *verified*, given there's no live wire tool for it?** Not a wire protocol question — checked directly against ch. 3.2 again: "the contract is fixed before the exchange begins... mutually agreed by both sides." The negotiation (and the byte-identical file itself) happens out-of-band, before any code runs — each team independently commits the *same*, pre-agreed file to their own GitHub repo (rule 4). `check_config.py --identical ours.json theirs.json` is the check, run by fetching both repos' files — an administrative/audit step a human (or a script either side runs manually) performs, not something either `Orchestrator` calls over MCP. PRD 6's actual job for rule 11 is narrower than it sounds: make sure this check is a required, recorded part of the pre-game ritual.

**Config SHA-256 in Step-0 is this repo's own addition, not book-required — stated plainly rather than left implicit.** Ch. 5.5's own Step-0 field list (p.55), read again precisely for this pass: hardware spec (OS/CPU/RAM/GPU), the LLM model name, the code's git-commit hash (rule 53), the group name, and "the game number" (`sub_game_number`, matching `config/game.toml`'s own existing field — not a generic `game_id` string, corrected from the first draft of this section). No config-file hash anywhere in that list. Including one anyway is a defensible design choice this repo is making, not a book requirement being surfaced: it closes rule 11's actual enforcement gap (a config swapped *after* Step-0 becomes a catchable audit-time mismatch, the same mechanism as everything else in this layer) at the cost of one field the book never asked for. Labeled as this repo's own extension in the `Step0Declaration` dataclass's own docstring when built, same "book-required vs. this team's own choice" discipline already used for the belief-map reliability coefficient (`todoFullFix.md` §E).

**4. State machine shape.** `state_machine.py`'s own docstring cites ch. 8, Fig. 11 as the target — re-read directly this pass (it hadn't been personally re-verified before the first draft of this section), and the book's own code sample (p.80) is exact, not paraphrased here:

```python
TRANSITIONS = {
    "WAITING_FOR_OPPONENT": {"COMPUTING_MOVE"},
    "COMPUTING_MOVE": {"COMMITTING", "TECHNICAL_LOSS"},
    "COMMITTING": {"AWAITING_REVEAL"},
    "AWAITING_REVEAL": {"VERIFYING", "TECHNICAL_LOSS"},
    "VERIFYING": {"WAITING_FOR_OPPONENT"},
    "TECHNICAL_LOSS": set(),  # terminal state
}
```

Five legal states in a cycle (Fig. 11's own caption, p.79: "the machine moves cyclically between: waiting for the opponent, move computation, commitment, waiting for reveal, and verification") plus the terminal state. Two things a first pass at this section got wrong and are corrected here: there is no `AWAITING_ACK` state and no `TURN_RESOLVED` state anywhere in the book — `Acknowledge` (ch. 5.3.2) maps onto the *existing* synchronous MCP ack (`receive_commit`'s own return value), not a fifth state, matching this repo's request/response transport for free; and the state after reveal is named `VERIFYING`, the book's own vocabulary, not a repo-invented name.

**`VERIFYING` is a real per-turn state, not an end-of-game-only phase** — `AWAITING_REVEAL → VERIFYING → WAITING_FOR_OPPONENT` happens every turn. This has to be reconciled against rule 18 (nonce secret until game end, **[FATAL]**, absolute) and ch. 5.3.2's own "only at the end of the game are all Nonce values revealed, for the sake of a complete mutual audit": per-turn `VERIFYING` *cannot* be the full cryptographic `Hcommit` check, because the nonce needed to recompute it doesn't exist yet at that point in the game. The only reading that keeps both chapters true simultaneously: per-turn `VERIFYING` is a **lightweight, structural check** — the reveal arrived, is well-formed, the claimed move is at least locally legal — genuinely different from, though same-named-in-spirit as, the full end-of-game mutual audit (ch. 5.4), which stays exactly what Design Question 2 already resolved: a separate, one-time process (`integrity/audit.py`), not a state in this per-turn table at all. `PeerStateMachine.transition("VERIFYING")` fires every turn as a real state; `integrity.audit.run_mutual_audit` is called once, at game end, outside the state machine entirely.

**Not every state reaches `TECHNICAL_LOSS`** — a claim the first draft made without checking it against the actual table. Only `COMPUTING_MOVE` and `AWAITING_REVEAL` do, in the book's own example. Fig. 11's own caption (p.79) says dashed arrows represent "emergency exits... from a communication step that failed" — broader than what the literal code table shows, an internal contradiction between the book's own diagram prose and its own code sample. Per `RULES.md`'s precedence rules (#2: illustrative code isn't binding by itself; #3: document the chosen reading when the book contradicts itself) and rules 6/7 (deadline-tracking/watchdog protection is independently binding for any wait on the opponent) — the defensible position, and the one this repo takes: extend the book's own table with exactly one additional edge, `COMMITTING → TECHNICAL_LOSS` (a send that can itself hang or fail, the same shape of risk `SENDING`'s pre-PRD-6 `TECHNICAL_LOSS` edge already covered), and leave `VERIFYING`/`WAITING_FOR_OPPONENT` without one, matching the book's own table exactly — neither represents an active wait on a pending peer response once the reveal is already in hand (`VERIFYING`) or a specific pending response at all (`WAITING_FOR_OPPONENT`, idle between turns). This is a real, argued deviation from the book's literal illustration, not a silent one — recorded here, and again in the module docstring once built, per this project's own "document contradictions and the reasoning" discipline.

**5. Does the scent map need its own commitment, given `RULE-19-SCENT-AUDIT-AT-PRD-6` names `verify_scent_map_against_commit`?** Yes — a real, new extension, not reopening the frozen `State` spec. `PRD-6-prep-commit-payload-spec.md` explicitly excluded `scent_field`/`belief_map` from `State` on float-safety grounds (dense floats, cross-peer hash mismatch risk) — that exclusion stands. What's added instead: a **separate commitment**, computed once per turn alongside `Hcommit`, hashing the canonicalized `share_scent_map` payload about to be sent (`tools/scent_wire.py::serialize_scent_field`'s own output is already integer/float-tuple-shaped and JSON-canonicalizable — the same `sort_keys=True, separators=(",", ":")` treatment, applied to the *serialized wire form*, not raw floats compared for equality after re-parsing). `verify_scent_map_against_commit(claimed_field, commit_hash)` re-serializes `claimed_field` the identical way and compares hashes — never compares floats directly, sidestepping the exact trap `PRD-6-prep-commit-payload-spec.md` was written to close.

**6. Capture claim/response — same commit-reveal machinery, or something lighter?** Same machinery, deliberately — rules 21/22 are both **[FATAL]**, no weaker standard than moves get. `claim_capture`/`respond_to_capture_claim` (`integrity/capture_protocol.py`) produce plain, honest-by-construction local objects; the *wire* trust comes from folding both the claim and the response into that side's own next `Hcommit` cycle, audited exactly like everything else at game end — not a parallel, separately-engineered honesty mechanism.

## Also verify (acceptance criteria, checked once built)

- `check_config.py --identical` passes on the two teams' actual committed files before any game is played, and the resulting SHA-256 is the one recorded in Step-0
- Nonces come from `secrets.token_hex`, never `random` — a grep-the-source check, same discipline as PRD 4's coordinate sweep
- The commit payload is canonical JSON (`sort_keys=True, separators=(",", ":")`) — both peers hash byte-identical input given the same logical envelope
- The nonce genuinely never crosses the wire before `receive_final_reveal` — inspect every trace event up to that point
- Hash comparison uses `secrets.compare_digest`, never `==`
- A deliberately tampered log **fails** the audit — the adversarial milestone, not optional
- Step-0's declaration carries the exact commit hash being played (rule 53) and is itself signed
- `verify_scent_map_against_commit` catches a tampered field (the guard test's own scenario) and accepts a genuine one
- `grep -rn RULE-15-16-BARRIER-DECLARATION-AT-PRD-6 RULE-21-22-CAPTURE-CLAIM-AT-PRD-6 RULE-19-SCENT-AUDIT-AT-PRD-6 src/ tests/` returns nothing once this layer lands
