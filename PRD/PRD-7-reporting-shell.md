# PRD 7 — Reporting and visualization shell

Status: **Built & verified, with two acknowledged, scoped gaps.** 418 tests, 99.87% coverage (the two remaining lines are `gmail_sender.py::get_service`'s real OAuth call, deliberately untested — no live Gmail credentials exist in this environment, documented in the test file's own module docstring rather than mocked to pad the number), `ruff check .` clean, `rule-auditor` run against the full rule set this layer owns, `check_config.py` passing, `scripts/watch_prd7_live_gui.py` and `scripts/watch_prd7_replay.py` both run live end-to-end (including the adversarial `TAMPERED` case). This is the largest layer by rule count in the project (26 of the 55 rules: 8, 9, 20, 28-38, 39, 40, 41-45, 49-52, 54, 55) — but most of that count is administrative (submission mechanics, Moodle, git tagging), not code. The **Build** list of six things is all built: the Live GUI, the Replay Viewer, the genuinely bilateral mutual audit closing PRD 6's own "Known gap," Gmail reporting over OAuth 2.0, the `ApiGatekeeper` facade, and the league/game-count bookkeeping the reports depend on. **The two gaps, found by `rule-auditor`'s own review, not silently missed:** (1) no automatic end-of-game sequence exists anywhere in `src/` that actually calls `run_mutual_audit`/`run_peer_audit`/`send_report_bundle` together — every component is correct and tested in isolation, but nothing chains them into one real trigger; rows 32/36 above originally overclaimed this and are corrected. (2) The capture-claim/response protocol (rules 21/22, built in PRD 3/PRD 6, not this layer) is still never called from the live `take_turn()` loop and `on_capture_claim`/`on_capture_response`/`on_barrier_declaration` are still never wired into `build_server()` — a pre-existing gap from before PRD 7, not a regression introduced here, but one PRD 7's own audit surfaced because rules 21/22 are nominally on this layer's rule list. Neither gap blocks this layer's own milestone (below), which is scoped, same as every prior PRD, to what's testable within this repo's own two-`Orchestrator` harness without a live cross-repo match. Full detail in Retrospective, below the Design Questions.

This is the layer that turns "we built a peer that cannot get away with being dishonest" (PRD 6) into "we built a peer that *shows its own honesty*, on screen and on paper." Every prior PRD's belief map, commit hash, and audit result has existed only as data a human would have to read code to see. PRD 7 is where that becomes: a live heatmap a human watches, a Replay Viewer that stamps `Verified OK` or `TAMPERED`, and a signed JSON report that reaches the lecturer's inbox automatically, rate-limited so it never gets the account blocked.

## Build

- **`src/cop/observability/live_gui.py`** — the Live GUI (ch. 7.3): a local-truth-only window showing this agent's own belief-map heatmap (deeper red = higher believed opponent probability, directly reusing `memory/belief.py::BeliefMap`) and a turn-state banner (green "YOUR TURN" when a peer's commit has just arrived, gray "LOCKED" once this side's own commit has been sent — ch. 7.3.2, Fig. 9). Tkinter, stdlib, no new dependency (Design Question 1).
- **`src/cop/observability/replay_viewer.py`** — the Replay Viewer (ch. 7.4, rule 20 **[FATAL]**): reads a recorded `log_<game_id>_g<NN>.json`, lets a human step forward/backward through it, and recomputes each step's `Hcommit` via `integrity/commit_reveal.py`'s real 7-field envelope and `integrity/audit.py::run_mutual_audit` — **not** ch. 7.5's illustrative 2-field `SHA256(nonce|move)` sketch (Design Question 4). Stamps `Verified OK` (green) or `TAMPERED` (red) and disqualifies the match on the first mismatch, no appeal (ch. 7.4's own wording). A second, human-facing consumer of the audit results built below — it visualizes what the automatic end-of-game sequence already computed, it does not itself trigger the audit (Design Question 11).
- **`src/cop/integrity/peer_trace.py`** — closes PRD 6's own "Known gap" for real, not just documents it further: persists the peer's own committed-and-revealed data — `on_commit`'s `h_commit`, `on_reveal`'s `move`/`hint_text` (`orchestrator_turn.py::_on_reveal_received` currently discards `move` entirely; extended here to persist both, keyed by step), and `on_final_reveal`'s disclosed nonces — structurally parallel to this side's own `committing`/`revealed` trace entries. `run_peer_audit(peer_trace, ...) -> AuditResult` reconstructs the peer's own `CommitEnvelope` from these three sources and runs it through the same `commit()`/`verify()` this repo's own self-audit already uses — the genuinely bilateral half of ch. 5.4's mutual audit (Design Question 11), which PRD 6 explicitly left for "whichever layer next needs a real end-to-end match." Wired into an automatic end-of-game sequence (not GUI-triggered) — ch. 5.4's own text places this audit at game's end, for every game, not as something a human opens the Replay Viewer to run.
- **`src/cop/observability/cost.py`** — token-total aggregation (rule 54): reads the trace log's own per-turn LLM token counts (currently only ever `0`, honestly, since `template`/`ollama` are the only implemented providers — Design Question 6) and rolls them up per sub-game and per series for the final JSON report.
- **`src/cop/policy/token_bucket.py`** — the book's own `TokenBucket` class (ch. 9.3.2, p.77's worked code) verbatim in shape: `tokens ← min(C, tokens + r·Δt)`, `allow() ⇐⇒ tokens ≥ 1`. Parameters sourced from `rate_limiter_gatekeeper.requests_per_minute` (Design Question 5).

## Milestone

A game summary can be sent by Gmail (a real OAuth 2.0 send, `token.json` reused after the first consent flow, the JSON report attached — never body text) through `ApiGatekeeper.execute()`, observably (its queue-status/log reflects the call) — demonstrated by a fake-service integration test (`test_a_transient_failure_through_the_gatekeeper_retries_then_succeeds`), **not yet by a live send with real OAuth credentials or by an automatic end-of-game trigger**; see Retrospective. The Live GUI displays belief-map state for a real, live exchange between two `Orchestrator` instances. The Replay Viewer reconstructs a recorded round from a real trace log this repo's own `Orchestrator` produced, stamping `Verified OK`. Two real `Orchestrator` instances exchange a full commit-reveal-final-reveal cycle and each side's own `run_peer_audit` genuinely verifies the *other's* committed-and-revealed data (Design Question 11) — the bilateral half of ch. 5.4, not just the self-audit PRD 6 alone produced. A **second, adversarial** milestone, matching this project's own "a verifier that has never rejected anything is indistinguishable from a broken one" rule: feed the Replay Viewer a tampered log and confirm it stamps `TAMPERED` and refuses to call it verified — not just that the honest path passes.

## Design questions answered here (not in code)

**1. GUI framework — Tkinter, not PyQt.** Ch. 7.3's own text names both as illustrative options ("כגון ייעודי GUI ]Tkinter או PyQt[" — "such as a dedicated GUI [Tkinter or PyQt]"), not mandating either. Tkinter is stdlib — no new dependency, matching this project's own preference (PRD 6's "New dependency: None" precedent) — PyQt would add one for a window that only ever needs a heatmap grid and a text banner, well within Tkinter's own capability. The Replay Viewer (Design Question 4) uses the same toolkit, for the same reason.

**2. The exact local-truth boundary, and how "Also verify" actually checks it.** Ch. 7.2's own principle, read precisely: "the GUI... shows each agent only what's *accessible* to it — its own position, the scent it sensed, the hints it received — never the full/objective board state... there is no 'bird's-eye view' that shows both sides' positions simultaneously." Concretely, `live_gui_render.py::render_state`'s call receives exactly six things, every one of them local-truth-safe: this side's own `Position`, `BeliefMap._probabilities` (a `dict[Position, float]`, already the whole point of the Bayesian layer since PRD 4), the `PeerStateMachine`'s current state string for the turn banner, this side's own placed barriers, `ScentField.full_field()` — this side's own currently-sensed scent, a second full-board `dict[Position, float]` rendered as its own blue heatmap panel, distinct from belief's red — and `hint_text`, the most recent hint text this side actually *received* from the opponent (`Orchestrator._last_hint_received`, mirrored there by `_on_reveal_received`), shown as a label under the turn banner. It never receives `GameState.target_pos` (belief, already filtered) and never receives the *true* thief position at all — this repo's own `Orchestrator` never even holds that value (rule 1/2: the true opposing position exists only inside the opponent's own separate process). `PLAN.md`'s own "Also verify" line for this rule ("check this by reading what data reaches the render call, not by looking at the screen") is the actual test discipline: a unit test inspects `render_state`'s own argument list/call site via introspection or a spy callback, not a screenshot.

**3. The turn-state banner reuses `PeerStateMachine` directly — no parallel GUI-only state.** Ch. 7.3.2, Fig. 9: green when "a commit has just arrived from the peer over MCP" (this repo's own `WAITING_FOR_OPPONENT → COMPUTING_MOVE` transition, i.e. a turn is now this side's to take), gray/"LOCKED" once "this side's own commit has been sent" (`COMMITTING` onward). Rather than inventing a second, GUI-specific state concept that could drift from the real one, `live_gui.py` reads `Orchestrator.state_machine.state` directly and maps it: `{WAITING_FOR_OPPONENT: not-yet-my-turn, COMPUTING_MOVE: "YOUR TURN", COMMITTING/AWAITING_REVEAL/VERIFYING: "LOCKED"}`.

**4. The Replay Viewer's verification engine reuses PRD 6's real machinery, not ch. 7.5's illustrative sketch.** Ch. 7.5's own code (`verify_step`, p.57-58) hashes only `f"{nonce}|{move}"` — a deliberately simplified 2-field version for exposition. Per `RULES.md`'s precedence rule #2 (illustrative code isn't binding), and matching PRD 6's own DQ1 precedent (the book's illustrative 4-field `Hcommit` equation vs. this repo's real 7-field envelope), the Replay Viewer calls `integrity/commit_reveal.py::commit()`/`verify()` against the same `state`/`move`/`intent`/`nonce`/`hint_text`/`step`/`role` envelope every other layer already uses, and `integrity/audit.py::run_mutual_audit` for the full-log pass — not a second, parallel, narrower verifier that could silently diverge from the real one. The book's own closing note (p.58) explicitly anticipates this: "the sketch simplifies the input for demonstration purposes; in practice, the signature covers all step components... as detailed in the protocol from ch. 5."

**5. Token-bucket parameter mapping — already resolved by `PLAN.md` §5, cited not re-derived.** `PLAN.md`'s own "Gatekeeper numeric precedence" note: the guide's illustrative `ApiGatekeeper` config (`concurrent_max: 5`, `retry_after_seconds: 30`) doesn't match Table 19 (`concurrent_requests: 2`, `retry_backoff_sec: 5`) — Table 19 is a locked MINIMUM under Appendix F and wins for every value it defines; the guide's numbers illustrate the pattern's *shape* only. `requests_per_minute` (30) maps to the book's own `r` (converted to per-second: `30/60 = 0.5`); `concurrent_requests` (2) is a **separate** gate from the token bucket's own `C` (burst capacity) — a semaphore-style "at most N in-flight calls simultaneously," not the same concept as "how many tokens can accumulate." `queue_depth` (100) bounds how many *waiting* calls `get_queue_status()` will report before the Gatekeeper itself starts rejecting outright rather than queuing. `C` itself isn't a named Table 19 field — this repo's own choice (Design Question 9), set equal to `requests_per_minute` (one full minute's allowance as the burst ceiling): a defensible, conservative reading, not a book-mandated number.

**5a. Three kinds of "token" appear in this layer, and the book itself warns never to confuse them (ch. 9.3.1, p.89, explicit):** rate-tokens (this section's own `TokenBucket` — load/capacity units, entirely unrelated to any language model), LLM tokens (`observability/cost.py`'s own concern, rule 54 — text-consumption units from a hint-generation call), and OAuth tokens (`gmail_sender.py`'s Access/Refresh Token pair, Appendix A). `rate_limiter_gatekeeper.requests_per_minute` governs the first only; `network_and_league.token_budget_per_series` governs the second only; neither reads from or writes to the other's config block. From here on in this doc, "token" alone means rate-token unless a paragraph says otherwise, matching the book's own convention.

**6. `observability/cost.py` reports `0` honestly under `template`/`ollama`, and that's correct, not a gap.** Table 21 states plainly both modes cost zero tokens; rule 54 requires reporting *actual* consumption, not requiring non-zero consumption. `hint_providers.py`'s existing `ClaudeApiHintProvider`/`ClaudeCliHintProvider` stubs (interface-only, raising `NotImplementedError`) are where real token counts would eventually originate if either provider gets built for real (Explicitly out of scope, above) — `cost.py` itself doesn't need to guess at a number no call ever produced.

**7. The DOS detector's exact statistic is this repo's own choice — the book gives the concept, not the number.** Ch. 9.3.1 names the pattern ("a statistical anomaly detector on the sending pattern... the same principle as backpressure/circuit-breaker known in system design") without specifying a threshold. This repo's own choice, labeled as such (same "book-required vs. this team's own choice" discipline as the belief-map reliability coefficient and Step-0's `config_sha256`): N consecutive Gatekeeper-approved sends within a short rolling window with no successful Gmail response in between trips `LOCKED` — a simple, auditable circuit-breaker condition, not a claim that this is the book's own prescribed formula.

**8. `report_bundle.py` composes `Step0Declaration`, it doesn't duplicate it.** Ch. 9.3.3's "declaration file" is described as broader than Step-0's own scope (hardware/code/config-hash) — it additionally carries team members, both sides' repo URLs, the agreed token ceiling, and start/end times. Rather than growing `Step0Declaration` itself (a PRD 6-owned, already-tested, narrowly-scoped dataclass — reopening it here would be exactly the kind of scope creep PRD 6's own "don't reopen the frozen spec" discipline warns against), `report_bundle.py` builds a separate, larger declaration object that *embeds* a `Step0Declaration` as one of its own fields plus the league-facing additions, sourced from `PrivateConfig` (which already has `group_name`, `members`, `repos`) and `policy/league_ledger.py`.

**8a. All four Table 20 files travel in one end-of-game email, not two separate sends.** Ch. 9.3.3, read precisely: the four JSON files are described together as "covering the game's full life-cycle" and attached to the same automated report. `report_bundle.py` builds both `declaration_<game_id>.json` and `result_<game_id>.json` for a single `gmail_sender.py::send_report` call that attaches all four (declaration, config, log, result) — there is no separate declaration-time send at game start.

**8b. The "four links" requirement (rule 49) is textually tied to the result file, not clearly to the declaration file too.** Ch. 9.4's own wording places "the file submitted at game's end... must include the four links" directly after describing the mutual, agreed-upon outcome — the **result** file (Table 20: "used to weight the league score"), not the declaration file. `ResultBundle` carries all four links (this team's cop+thief, the opponent's cop+thief) because the book requires it there; `DeclarationBundle` carrying the same four is this repo's own conservative redundancy, not something ch. 9.4 asks of that specific file — labeled as such rather than presented as equally book-mandated.

**8c. `PrivateConfig.email_mode` (`"draft"`/`"send"`) gets its meaning defined here, since nothing else does.** The field is loaded (`config/game.toml`'s `[email].mode`) but was never consumed by any prior layer. `"draft"` builds the full report bundle and the `MIMEMultipart` message but stops short of calling `gmail_sender.py`'s actual Gmail `send` — the safe default for local development without live OAuth credentials. `"send"` performs the real send. `gmail_sender.py`'s own top-level orchestration branches on this value; neither `report_bundle.py` nor the Gatekeeper needs to know about it.

**8d. The trace log's filename must actually match Table 20 for a real game — `PLAN.md`'s own claim that it already does is wrong.** `PLAN.md` states "the config/log names already match what this repo uses"; checked directly against `orchestrator.py`, `Orchestrator.__init__`'s actual default is `log_path: str = "logs/trace.jsonl"`, not `logs/log_<game_id>_g<NN>.json`. The config file's own default does match (`config_dev_g01.json` already follows `config_<game_id>_g<NN>.json`); the log file's default does not. `log_path` is already a constructor parameter, not hardcoded, so this needs no code change — but whatever this layer's own end-of-game orchestration script constructs a real-game `Orchestrator` with must pass the correctly-formatted path explicitly, and `report_bundle.py` should not assume the default is already correct. (Also corrected at the source: `PLAN.md`'s own line now states this precisely rather than claiming false consistency.)

**9. No separate `config/rate_limits.json` — Table 19's own block in the negotiated config wins.** `software_submission_guidelines-V3.pdf` §7.3 wants a standalone, versioned `rate_limits.json`. `rate_limiter_gatekeeper` already exists as its own section inside `config/shared/config_<game_id>_g<NN>.json` (Appendix B, confirmed present in `config_dev_g01.json` today) — cryptographically locked and byte-identical between peers already, for free. Per `CLAUDE.md`'s own precedence rule ("where the guide's number conflicts with Appendix F, Appendix F wins — the guide's numbers illustrate the pattern's shape, not override the game's locked parameters"), `policy/gatekeeper.py` reads its limits from the existing negotiated config, not a new file.

**10. The Gmail message is `MIMEMultipart`, not the book's own bare `MIMEText` sketch.** Ch. 9.3's code example (p.124) builds a `MIMEText(body)` — a plaintext-only message, useful for illustrating the OAuth send mechanics but not the actual required report shape. **11. The mutual audit (rule 36) is genuinely bilateral — re-read ch. 5.4 precisely for this pass, and PRD 6's own self-audit alone doesn't satisfy it.** Ch. 5.4's own text: "for each side, the Nonce disclosure enables reconstructing **the opponent's** data — it takes the SHA-256 of the State, Move, Intent, and Nonce **the opponent disclosed**, recomputes them, and compares the result to the signature announced at the commitment stage." PRD 6's own retrospective already named this precisely: *"This audits this side's own log against this side's own later-revealed nonces — the self-consistency half... Closing this gap for real... is unstarted work for whichever layer next needs a real end-to-end match, not assumed done by this one."* PRD 7 is that layer — but genuinely closing it needs three things wired together, not just one: `_on_reveal_received` (`orchestrator_turn.py`) currently discards the peer's own `move` entirely (`del move  # unverified claim... not consumed here`) — extended here to persist `(move, hint_text)` keyed by step; `on_commit` (PRD 6's own "Known gap") gets wired to persist the peer's `h_commit` per step; `on_final_reveal` gets wired to persist the peer's disclosed nonces per step. `integrity/peer_trace.py::run_peer_audit` reconstructs the peer's own `CommitEnvelope` from these three sources and runs it through the same `commit()`/`verify()` this repo's own self-audit already uses. This is fully buildable and testable within this repo's own existing two-`Orchestrator`-instances-talking-to-each-other pattern — same honest scope every prior PRD's own milestone already uses — it does **not** require a live match against the actual separate thief repo, so PRD 7's own "no live two-repo match" exclusion doesn't block it. `run_mutual_audit` (self) and `run_peer_audit` (bilateral) are complementary, not redundant: the self-audit catches this process's own bugs (already adversarially tested, PRD 6); the peer-audit catches the *opponent's* dishonesty, which is what rule 19/36 actually exist to catch.

## Retrospective

Written at closing, after `rule-auditor`'s own full-layer review — same discipline PRD 6's own retrospective established: name what the audit actually found, correct any row that overclaimed, don't silently absorb the gap.

**What actually got built and verified.** All six Build items exist, are unit-tested (418 tests, 99.87% coverage across the full repo), and were watched running live end-to-end for the two items that have a visible-behaviour component: `scripts/watch_prd7_live_gui.py` (a real belief-map render across three real turns, including the negative-probability color-clamping bug this run itself found and fixed) and `scripts/watch_prd7_replay.py` (both the honest `Verified OK` path and the adversarial tampered-log `TAMPERED` path). The genuinely bilateral mutual audit (Design Question 11) is adversarially tested end-to-end (`test_a_tampered_peer_move_fails_the_bilateral_audit`), closing PRD 6's own named gap for real, not just in design. Four separate sanity-check-by-sabotage passes were re-run at closing (Gatekeeper skipping a gate, a tampered Replay Viewer log, a widened Gmail scope, `run_peer_audit` faked into always passing) and every one was genuinely caught by its corresponding test, not just assumed to be.

**Gap 1 — no automatic end-of-game sequence.** `rule-auditor`'s own grep across `src/` and `scripts/` found that `send_capture_claim`, `send_capture_response`, `send_final_reveal_to_peer`, `audit_peer`, `send_report`, `send_report_bundle`, and `ApiGatekeeper(` are each called only from their own module's unit tests — nothing calls them together, in sequence, at the end of a real game. Rows 32 and 36 of the Rules owned table above originally claimed this sequence exists ("called once per finished game", "the automatic end-of-game sequence runs both..."); both were corrected during this closing pass once the audit showed the claim was false. This is a real, code-level gap, not an admin/honesty one: every piece is individually correct and tested, but there is no orchestration function that chains "game ends → run both audits → build the bundle → send it through the Gatekeeper" into one call. Closing it is a bounded, well-scoped next task (an `end_of_game(peer_url)` method, most naturally added to `orchestrator_peer_audit.py` or a new sibling mixin) — deliberately not built in this pass rather than added without a PRD/TODO line for it first, per this repo's own house rule of writing the design down before writing the code.

**Gap 2 — the capture-claim/response protocol is unwired from the live turn loop.** `domain/capture.py` (PRD 3), `integrity/capture_protocol.py` and the `mcp_server_prd6.py`/`mcp_client_prd6.py` capture-claim/response tools (PRD 6) are all built and unit-tested, but `orchestrator_turn.py::take_turn()` never calls `is_coordinate_capture`/`is_barrier_capture`/`thief_has_no_legal_move`, never calls `claim_capture()`, and never calls `send_capture_claim()`; `orchestrator.py`'s own `build_server()` call never passes `on_capture_claim`/`on_capture_response`/`on_barrier_declaration`, so they default to `None` and a peer's real capture claim would be silently acknowledged and discarded. This predates PRD 7 — it was never closed in PRD 3 or PRD 6 either — but PRD 7's own Rules-owned table lists rules 21/22 as belonging to this layer (they don't; they're PRD 3/6 rules PRD 7 never actually took on), so `rule-auditor`'s full-rule-set pass surfaced it here. In a real networked match today, this cop can neither truthfully declare a capture it made nor act on a capture claim the thief sends. Also deliberately left unbuilt in this pass, for the same reason as Gap 1 — this is new scope, not a PRD 7 checklist item, and belongs behind its own PRD/TODO before code, not silently absorbed into a closing cleanup pass.

**Both gaps share one root cause worth naming plainly:** every PRD from 3 onward built and tested its own slice against this repo's own two-`Orchestrator`-test-harness pattern (rule 1/2: no thief brain here, so "the peer" in every test is a second cop instance) — a deliberate, repeatedly-stated scope boundary ("no live two-repo match" appears in PRD 5's, PRD 6's, and this layer's own "Explicitly out of scope" sections). That pattern proves each component correct in isolation. It has never proven that a *complete* real game — capture through to a mailed report — actually runs end-to-end, because nothing has yet needed it to. The first layer that does need it (a real counted game against the actual thief peer) will need both gaps closed first.
