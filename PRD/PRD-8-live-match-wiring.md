# PRD 8 — Live match wiring

Status: **Built & verified.** 438 tests (430 unit + 8 integration), 99.88% coverage (the one remaining gap is `gmail_sender.py::get_service`'s real OAuth call, deliberately undoctored since PRD 7 — no live Gmail credentials in this environment), `ruff check .` clean, `check_config.py` passing, `rule-auditor` run against this layer's own rule set (see Retrospective below for findings). `scripts/watch_prd8_live_match.py` run live end-to-end: a real, wire-confirmed `Outcome.CAPTURE` ending a match in exactly one turn, and a denied claim continuing an otherwise-identical match to an ordinary `SURVIVAL` ending — both cases, `report_game()`'s own automatic end-of-game sequence running immediately after in both.

**Corrected during this layer's own critique pass, before any TODO8 line was written against it** — the first draft's Build section proposed a new state-machine state (`AWAITING_CAPTURE_RESPONSE`) that turns out to be unreachable given the call sequence that same draft described, and omitted two attributes (`self.log_path`, `self.league_ledger`) `report_game()`'s own Build bullet already assumed existed. All three are fixed below, cited against the actual current source, not re-paraphrased from the first draft. **Two further, more significant findings surfaced only once the real tests actually ran** (not from the critique pass, not from design review) — a genuine cross-event-loop `asyncio.Event` thread-safety bug, and a pre-existing, unrelated test that started hanging once real capture claims could fire during ordinary multi-turn play. Both are detailed in the Retrospective, not silently absorbed.

Not one of `PLAN.md` §5's original "seven layers," and not `PLAN.md` §6's "Optional Layer 8" (orchestrated between-game learning/RL) either — a distinct eighth layer, added because PRD 3, PRD 6, and PRD 7 each independently reached the same edge and each deliberately stepped back from it, in near-identical words:

- PRD 3 (`Design Question 3`): "commit-reveal wraps the *wire*, not the move-decision algorithm" — the live `Orchestrator.take_turn()` decides and sends **one turn**, full stop; nothing calls it in a loop, checks for game-over, or knows when the match is finished.
- PRD 6 (`Explicitly out of scope`): *"A live 'play N full turns end to end' game loop wired through commit-reveal — the milestone proves one committed-and-revealed move plus one full mutual audit on a short synthetic log, not a complete 35-step sub-game... Closing this gap for real... is unstarted work for whichever layer next needs a real end-to-end match, not assumed done by this one."*
- PRD 7 (`Explicitly out of scope`): *"A real, live two-repo match against the actual thief peer... [is] proven against a recorded log this repo's own `Orchestrator` produced... same 'no live two-repo match' scope boundary."*

This is that layer. Not triggered by a new rule reading — triggered by `rule-auditor`'s closing-pass review of PRD 7 (documented in `PRD-7-reporting-shell.md`'s Retrospective), which found two concrete, code-level consequences of the same deferred gap: the capture-claim/response protocol (rules 21/22, built in PRD 3/PRD 6) is never called from `take_turn()`, and no automatic end-of-game sequence chains the mutual audits, the report bundle, and the Gmail send together. Both findings turn out to share one root cause — **there has never been a live, multi-turn game loop at all**, only a single-turn function (`take_turn`) and a single-turn commit/reveal wrapper (`commit_and_reveal_to_peer`) — so this PRD's own Build section is organized around building that loop once, correctly, rather than patching each symptom separately.

## The three things this closes

1. **A live multi-turn game loop** — something actually calls `take_turn()` repeatedly, checks for game-over after each turn (capture or step-ceiling/survival-threshold), and stops when it's over. Nothing in this repo does this today outside `reasoning/subgame.py`'s offline, no-network sandbox (PRD 3), which was always scoped to algorithm correctness, not the wire.
2. **The capture-claim/response protocol, wired for real** (rules 21/22). `domain/capture.py`, `integrity/capture_protocol.py`, and the four MCP tools (`receive_capture_claim`/`send_capture_claim`, `receive_capture_response`/`send_capture_response`) are all built and unit-tested — but nothing decides *when* to call `send_capture_claim`, and `on_capture_claim`/`on_capture_response` are never passed to `build_server()`, so an incoming claim or response is acknowledged and silently discarded.
3. **The automatic end-of-game sequence** (rules 32, 36). `integrity/audit.py::run_mutual_audit`, `integrity/peer_trace.py::run_peer_audit`, `tools/report_bundle.py`, `tools/gmail_sender.py`, and `policy/gatekeeper.py::ApiGatekeeper` are each correct and tested in isolation (PRD 6/7) — nothing in `src/` calls them together, in order, when a game actually ends.

## Build

- **`src/cop/reasoning/state.py` or a new `orchestrator_capture.py` mixin** (150-line cap will decide the exact split) — a pure function, `claims_capture(action: Action, own_pos_before: Position, own_pos_after: Position, target_pos: Position) -> Position | None`: returns the claimed thief cell if this turn's action landed on the belief target (`Move` → `own_pos_after == target_pos`; `PlaceBarrier` → `action.target == target_pos`), else `None`. See Design Question 1 for why this is the correct, honest trigger given the cop never holds a true thief position to check against.
- **`src/cop/orchestrator_turn.py::take_turn`** — capture the belief target into a local variable (`believed_thief_pos = self.game_state.target_pos`) *immediately after* applying the move, *before* `self.game_state.target_pos` gets overwritten with the next turn's fresh belief a few lines later — the overwrite already exists (`self.game_state.target_pos = self.belief_map.most_likely_cell()`) and stays exactly where it is; only the capture is new. Thread `believed_thief_pos` through as a new parameter to `commit_and_reveal_to_peer` (below). Without this, the capture check would silently compare against next turn's belief instead of the one the brain actually used to decide this turn's move.
- **`src/cop/orchestrator_commit_reveal.py::commit_and_reveal_to_peer`** — gains a `believed_thief_pos: Position | None` parameter. Inside the existing `AWAITING_REVEAL` window — sibling to the barrier-declaration block that already lives there (`orchestrator_commit_reveal.py:97-118`), same reasoning PRD 6 already established for exactly this shape of bug (see Design Question 2) — if `claims_capture(action, own_pos_before_this_turn, self.game_state.own_pos, believed_thief_pos)` returns a claimed cell: build a `CaptureClaim` (`integrity/capture_protocol.py::claim_capture`), send it (`send_capture_claim`), then await the peer's own independent `CaptureResponse` callback with a deadline (`await_with_deadline(self._capture_response_event.wait(), timeout_seconds=self.config.response_timeout_seconds)`) — still entirely within the `AWAITING_REVEAL` state, so a timeout reaches `TECHNICAL_LOSS` via the edge that state *already has*, no new edge required. `commit_and_reveal_to_peer`'s own return type is unchanged (still `result`, the reveal ack — not a breaking-change candidate, since every existing caller/test already depends on that shape); the outcome of the capture check instead sets `self._last_turn_captured: bool`, reset to `False` at the top of every call, set `True` only on a genuine `confirmed=True` response — `play_game()` (below) reads this attribute after `take_turn()` returns, never guesses at a return-value shape that was never actually changed. A timeout or `confirmed=False` leaves it `False` and is not a failure — the game continues normally, since the claim itself never asserted certainty (Design Question 1).
- **`src/cop/orchestrator.py`** — `self._capture_response_event: asyncio.Event`, `self._capture_response: CaptureResponse | None`, `self._last_turn_captured: bool = False`, all reset before each claim is sent. `self.log_path = log_path` (the constructor parameter — currently only forwarded into `self.trace = Trace(log_path)`, never kept on `Orchestrator` itself; `report_game`, below, needs it). `self.league_ledger = LeagueLedger()`. `build_server()`'s call gains `on_capture_response=self._on_capture_response_received` (sets the event) and `on_capture_claim=self._on_capture_claim_received` (Design Question 3 — a defensive no-op/log-and-ignore path, since this repo's own role never legitimately *receives* a claim in this game's own scoring model).
- **`src/cop/orchestrator_game_loop.py`** (new mixin, `GameLoopMixin`) — `async def play_game(self, peer_url: str) -> Outcome`: the actual multi-turn loop. Each iteration: `await self.take_turn(peer_url)` (which now also runs the capture-claim exchange internally, per the `commit_and_reveal_to_peer` bullet above); `outcome = determine_outcome(captured=self._last_turn_captured, steps_taken=self.game_state.steps_taken, step_ceiling=self.config.step_ceiling, survival_threshold=self.config.survival_threshold)`; loop again if `outcome is None`, else break. `self.watchdog.heartbeat()` once per completed turn (every prior PRD's own "every wait on the opponent" discipline extended to the loop level, not just individual calls). Returns the final `Outcome`. **Left genuinely open, flagged for explicit resolution at execution time (found while drafting TODO8, not yet decided here):** `take_turn()` itself currently *raises* on a technical loss (`orchestrator_turn.py`'s own `except Exception` block transitions state, then `raise`s) — `play_game()` either catches that exception and converts it to `Outcome.TECHNICAL_LOSS` (matching this bullet's original intent, that a caller of `play_game()` never needs a `try/except` to learn the match ended), or `play_game()` re-raises like `take_turn()` already does and this bullet's claim of never raising is simply wrong. TODO8 §4 carries this as an explicit, undecided checklist item rather than picking one silently.
- **`src/cop/orchestrator_end_of_game.py`** (new mixin, `EndOfGameMixin`) — `async def report_game(self, peer_url: str, outcome: Outcome, is_counted: bool) -> dict | None`: called once, by `play_game`'s own caller (not `play_game` itself — Design Question 4), after the loop returns. Sequence: `await self.send_final_reveal_to_peer(peer_url)` → `self_audit = run_mutual_audit(self.log_path, self._pending_nonces)` → `peer_audit = self.audit_peer()` → `if is_counted: self.league_ledger.record_counted_game(opponent_id)` (the caller decides counted-vs-warm-up, not this method — Design Question 5) → build `ResultBundle`/`build_result` (`tools/report_bundle.py`, already built) → `ApiGatekeeper.execute(send_report_bundle, ...)` (`tools/gmail_sender.py`, already built, routed through the Gatekeeper per PRD 7's own rule 3/I2 discipline). Returns the Gmail send result (or `None` under `email_mode="draft"`).
- **Test/demo fixture only, not `src/`**: `scripts/watch_prd8_live_match.py` — two real `Orchestrator` instances, one driving `play_game()` against the other's server, ending in a genuine `Outcome.CAPTURE` (the `greedy_thief_mover`-shaped fixture already used since PRD 3, moved onto this repo's own belief target deliberately for the demo, same "test fixture only, never a shipped `thief_class`" boundary `PRD-3-blind-strategy.md`'s own Design Question 5 already established) — run and watched, not just asserted, matching this project's own "a layer is done when the behaviour was watched by a human" rule.

## Milestone

Two real `Orchestrator` instances play a genuine multi-turn match via `play_game()` — not a single hand-assembled turn, and not the offline `subgame.py` sandbox. The match ends in a real, wire-confirmed `Outcome.CAPTURE`: this side sends a `CaptureClaim`, the peer's own `respond_to_capture_claim` truthfully confirms it, `on_capture_response` receives that confirmation, and `determine_outcome` returns `CAPTURE` — not asserted from a hardcoded/faked capture flag. Immediately after, `report_game()` runs both audits, builds the result bundle, and sends it (through `ApiGatekeeper.execute()`, observably) — all three end-of-game rules (32, 36, and the audit half of 19) demonstrated running automatically, in sequence, for the first time in this project's history, not manually invoked one at a time as every prior PRD's own milestone left them. A **second, adversarial** case, matching this project's own "never trust a single test path" rule: a claim sent when the belief was wrong (the peer denies it, `confirmed=False`) does not end the game, does not trip a technical loss, and does not falsely count as rule 21 dishonesty — the game continues to a normal `SURVIVAL`/step-ceiling ending instead, demonstrated live alongside the capture case.

## Design questions answered here (not left for code-time guessing)

**1. What triggers a `CaptureClaim`, given the cop structurally never holds the true thief position (rule 1/2) — and how is that still "declaring only the truth" (rule 21)?** **Confirmed directly against the book** (text supplied by the user from the primary source, resolving the hedge this Design Question originally carried): *"A capture occurs when the Cop lands on the same cell as the Thief **and makes a capture claim**... Neither agent sees the true global world state or the opponent's exact position; each agent only has a local observation... When the Cop declares a capture, the Thief is placed under a strict cryptographic obligation to answer the truth... Any attempt by the Thief to lie or deny an actual capture is exposed during the post-mortem log audit and results in immediate technical loss/disqualification."* This confirms the reading already reached by re-checking `integrity/capture_protocol.py`'s own module docstring: the "same cell as the Thief" the book describes is necessarily the cop's own *believed* cell — the book itself pairs "lands on the same cell" with "**and** makes a capture claim" as two parts of one act, not "lands on the cell, and separately, already knows for certain it did," since the very next sentence establishes that neither agent ever sees the opponent's exact position. `CaptureClaim(thief_pos, cop_pos, claimed_at_step)`'s `thief_pos` field is the cop's own believed thief cell (the turn's belief target, `game_state.target_pos`), and `is_coordinate_capture(cop_pos, thief_pos)` evaluates trivially true by construction once claimed — `capture_protocol.py`'s own "already-true local fact" language holds exactly because the claim's own content, not the underlying belief, is what must be true. Rule 21 is satisfied by the declaration being honest about *what the cop observed and did*; the `CaptureResponse` — cryptographically obligated, checked at the post-mortem audit exactly as the book states — is what supplies the actual truth. A wrong belief produces `confirmed=False`, not a rule 21 violation, matching the book's own "exposed during audit" framing being about the *Thief's* honesty in answering, not the Cop's certainty in asking.

**2. The capture-claim/response exchange is not a simple request/response, unlike every other `send_*` call in this repo — what does that mean structurally, and does it need a new state-machine state?** Checked directly against `tools/mcp_server_prd6.py::receive_capture_claim`'s own docstring: *"Acknowledges receipt only — the truthful confirm/deny travels back later, as its own commit, via `receive_capture_response` (not this call's return value)."* Every other wire call in this repo (`send_commit`, `send_reveal`, `send_barrier_declaration`) gets its real answer as the awaited call's own return value. A capture claim gets only an ack back immediately; the actual `CaptureResponse` arrives later, as the peer's own independent, outgoing call to *this* side's server — genuinely asymmetric, closer in shape to the incoming connection PRD 2's watchdog already anticipates than to a normal RPC round trip. This needs a synchronization primitive `await_with_deadline` (already built, PRD 2/6) doesn't provide by itself for an *incoming* event: `self._capture_response_event: asyncio.Event`, set by `_on_capture_response_received` (the server-side callback), awaited via `await_with_deadline(self._capture_response_event.wait(), timeout_seconds=self.config.response_timeout_seconds)` — `Event.wait()` is itself a coroutine, so no new deadline machinery is needed.

**A first draft of this PRD proposed a new state-machine state, `AWAITING_CAPTURE_RESPONSE`, for this wait — corrected here, before any code was written against it.** That state would have been entered via `VERIFYING → AWAITING_CAPTURE_RESPONSE`, driven by a *separate* call (`claim_capture_if_warranted`) made from `play_game()`'s own loop *after* `take_turn()` returns — but `commit_and_reveal_to_peer` (the function `take_turn()` calls into) already unconditionally transitions all the way to `WAITING_FOR_OPPONENT` before returning (`orchestrator_commit_reveal.py:139`), so that edge could never actually fire; `VERIFYING` is long gone by the time such a call would run. The real fix needs no new state at all: PRD 6 already solved the identical shape of bug for barrier declaration, moving it into the `AWAITING_REVEAL` window specifically *because* that state (unlike `VERIFYING`) already has a `TECHNICAL_LOSS` edge (`PRD-6-security-and-cryptography.md`'s own retrospective, item 2). The capture-claim send-and-await belongs in that exact same window, sibling to barrier declaration (Build, above) — reusing `AWAITING_REVEAL`'s already-legal edge for this wait's own timeout path. This doesn't reopen or dispute PRD 6's own Design Question 4 claim that the five-state cycle is "exact, not paraphrased" against the book's Fig. 11: Fig. 11's five states are untouched by this change, exactly as they were already untouched by barrier declaration reusing the same window — rules 21/22's capture protocol is a second thing this repo layers onto that cycle, same category as rule 15/16's barrier declaration, not a revision of the cycle itself.

**3. Should this cop's own server ever *act* on an incoming `CaptureClaim` (`on_capture_claim`)?** No — checked directly against `domain/capture.py`'s own module docstring: *"the ways a sub-game ends in the **cop's favour**"* — there is no symmetric "thief captures cop" outcome anywhere in `domain/scoring.py`'s `Table 17` mapping (`Outcome.CAPTURE` always scores `score_capture_cop`/`score_capture_thief`, never the reverse). `capture_protocol.py`'s own docstring confirms this repo, as cop, only ever *sends* claims and *receives* responses — a `CaptureClaim` arriving at this side's own server would be unexpected, protocol-violating traffic from a misbehaving or buggy peer, not a legitimate game event this repo's own scoring model has any outcome for. `on_capture_claim`, once wired, is therefore a defensive no-op: log it (I9 — untrusted input, recorded not acted on) and return the existing `{"acknowledged": True}` ack `receive_capture_claim` already sends regardless — never attempt to fabricate a `CaptureResponse` about a position (`true_thief_pos`) this process cannot honestly assert, since it is not the thief.

**3a. Rule 47 (entombment — no legal moves left) is a second, distinct capture condition per the book's own text — does `claims_capture()` need to detect it separately?** The book states both conditions in one sentence: *"A capture occurs when the Cop lands on the same cell as the Thief and makes a capture claim, **or** when the Thief is cornered with no legal moves left"* — confirming rule 47 is not just a special case of the coordinate claim. Checked against `capture_protocol.py::CaptureClaim`'s own shape (`thief_pos`, `cop_pos`, `claimed_at_step` — no "entombed" flag or distinct claim type) and against `PRD-3-blind-strategy.md`'s own empirical retrospective finding (`## Entombment` section, PRD 3's second review pass): across 50 randomized full local subgames, `CopBrain`'s own greedy heuristic *never once* finished a game via a genuine zero-legal-moves entombment — "once only one gap remains, that cell is always the cop's single closest move... walking always wins the tie over sealing it," so the capture that finishes the job is empirically always a coordinate walk-in, even in a near-sealed position. Given this repo's own shipped `CopBrain` heuristic structurally never produces the situation a distinct entombment-claim wire path would exist to serve, and given `capture_protocol.py`'s own claim shape has no field for it anyway, building a separate entombment-claim mechanism is **out of scope for this PRD** — the same "book gives a concept this repo's own current strategy never actually exercises" category PRD 3 already used for the barrier-quota-exhausted branch. `claims_capture()` (Build, above) only ever checks the coordinate/barrier-target case; `thief_has_no_legal_move` stays exactly where PRD 1 left it — a real, tested predicate, reachable from the offline `subgame.py` sandbox where both true positions are known, not from the live wire path. Revisit only if a future, less-greedy `CopBrain` heuristic starts actually producing entombments that a coordinate walk-in doesn't already resolve first.

**4. Why is `report_game()` a separate call from `play_game()`, not folded into the same loop?** Matches the precedent every prior PRD already set for keeping algorithm-correctness/network-correctness/reporting-correctness independently testable (`PRD-3-blind-strategy.md`'s own Design Question 3, `PRD-7-reporting-shell.md`'s own two-`Orchestrator`-harness pattern): a test proving `play_game()` correctly reaches `Outcome.CAPTURE` should not also require a working `ApiGatekeeper`/Gmail mock to pass, and a test proving `report_game()` correctly sequences the audits and the send should not need to re-run an entire multi-turn match to set up its input — it can be handed a pre-built `Outcome` directly. The two are composed by a thin caller (the milestone script, and eventually whatever real entry point runs a counted game), not merged into one function.

**5. Does `report_game()` decide counted-vs-warm-up itself?** No — `policy/league_ledger.py::record_counted_game`/`declare_at_game_start` already exist and are this repo's own source of truth for that distinction (PRD 7); `report_game()` takes an `is_counted: bool` parameter from its own caller rather than re-deriving the policy, the same "don't reopen an already-frozen decision" discipline `PRD-7-reporting-shell.md`'s own Design Question 8 used for `Step0Declaration`.

## Retrospective

Written at closing, after `rule-auditor`'s own full-layer review — same discipline every prior PRD's own closing retrospective established.

**What actually got built and verified.** All three things this PRD closes are built, wired into live play, and adversarially tested: the first-ever live multi-turn loop (`play_game()`), the capture-claim/response protocol actually firing from real turns (not just built and unit-tested in isolation, PRD 6's own state), and the automatic end-of-game sequence (`report_game()`) chaining both audits, league bookkeeping, and the Gatekeeper-wrapped report send. `scripts/watch_prd8_live_match.py` demonstrates both the honest-capture case and the adversarial denied-claim case live, watched, not just asserted — the confirmed case ends a real match in exactly one turn; the denied case continues to an ordinary `SURVIVAL` ending at the step ceiling, in both cases `report_game()` running immediately after.

**The critique pass's own two corrections held up under construction** — Finding 1 (no new state-machine state; reuse `AWAITING_REVEAL`) and Finding 2 (capture belief-target must be captured before the overwrite) were both verified with dedicated sabotage tests during execution: reverting either fix reproduces exactly the failure the critique predicted (an unreachable state edge; a capture silently comparing against next turn's belief). Findings 3 and 4 (`self.log_path`, `self.league_ledger`) were straightforward one-line additions, confirmed correct by the tests that depend on them.

**Two real bugs found only by running the code, not by the critique or by design review:**

1. **`asyncio.Event.set()` is not thread-safe across event loops.** The claiming side awaits the capture-response event inside its own `asyncio.run(...)` call; the response arrives via this side's own MCP server, which runs in a genuinely separate OS thread with its own event loop. Calling `.set()` directly from the server's thread never wakes a waiter parked in a different loop — a real, reproducible hang, confirmed by running the adversarial test under an explicit `timeout 30` and watching it actually time out. This is the first place in this repo a server-side callback needed to wake a blocked client-side coroutine across threads — every prior PRD 6/7 callback only ever recorded data into instance dicts, nothing else was ever actively waiting on one. Fixed with `call_soon_threadsafe`, the standard cross-loop-safe signaling mechanism; `orchestrator_capture.py`'s own module docstring documents the reasoning in full.
2. **A pre-existing, unrelated test started hanging.** `test_step_index_agreement.py`'s 12-round lockstep test — never about captures, only step counting — began timing out because, over enough real rounds, a `CopBrain` peer's own move can legitimately land on its own belief target (the point of the strategy), triggering a genuine claim the other cop-instance peer never answers by design (Design Question 3). This is a structural consequence of rule 1/2's own test-harness limitation (this repo can never run a thief brain, so "the peer" in every bilateral test is always another cop, which can never honestly answer a capture claim) — not a flaw in the capture logic itself, and not something a real deployment would ever hit (a genuine thief peer answers honestly and promptly, per rule 22). Fixed by disabling capture detection for the one affected test's own duration; a targeted search confirmed no other existing test shares the same risk shape (multiple real, adaptively-decided rounds between two live `Orchestrator` instances).

**One further, genuinely plausible defect `rule-auditor`'s own closing-pass review found, not caught by any test:** `self._capture_response_loop` was being assigned *after* `send_capture_claim` was awaited — a response arriving in the (small, but real) window between the peer's ack and that assignment line would find `_capture_response_loop` still `None`, and `_on_capture_response_received`'s own defensive `if loop is not None` guard would silently skip waking the waiter, stalling the claiming side for the full deadline despite the response having already arrived and been recorded correctly. Fixed by moving the assignment to before the send, closing the window entirely — a one-line reordering, verified against the existing test suite (no behavior change on any passing path, only the race window removed).
