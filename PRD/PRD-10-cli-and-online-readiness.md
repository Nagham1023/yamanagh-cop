# PRD 10 — CLI entry point, complete report bundle, and online-match readiness

Status: **Built & verified.** 491 tests (483 unit + 8 integration), 99% coverage on `src/cop`. `uv run python -m cop peer` / `uv run python -m cop replay --log <path>` now exist and match `CLAUDE.md`/`README.md`'s own documented interface exactly. `ruff check .` clean, `check_config.py` still 33/33, secret sweep still empty. Two real, independent local processes reach a genuine negotiated, played, and reported match end to end through the CLI itself, not through hand-assembled `Orchestrator(...)` calls — including a literal two-process `uv run python -m cop peer` subprocess smoke test, not just the Python-level `run_peer()` tests. A `rule-auditor` pass scoped to rules 6/7/18/20/34/49 found one real, empirically-reproduced race condition and one filename inconsistency this layer's own first draft missed — both fixed before this status line was written (Retrospective, below).

Two gaps were named directly: (1) the CLI entry point (`CLAUDE.md`/`README.md` document it; PRD 7's own "Explicitly out of scope" section names the gap and defers it — never built until now). (2) `report_game()` attached only `result_<game_id>.json`, not all four Table 20 files — its own module docstring flagged this as a known simplification.

Designing the CLI surfaced a **third, load-bearing gap** neither item named: `self._pending_nonces` (what `run_mutual_audit`/`ReplayViewer` need to cryptographically verify a match) lived only in the live process's memory — `send_final_reveal_to_peer` logged `step_count=len(nonces)`, never the nonces themselves. A standalone `replay --log <path>` run against a completed match's log file, after the process that played it has exited — the entire point of a replay verifier per rule 20 — had no way to obtain them. Confirmed by direct reads of `orchestrator_peer_audit.py`/`integrity/audit.py`/`observability/trace.py`, not assumed. Fixed as part of this same layer, since it blocks the `replay` subcommand from working as documented and blocks the `log_` attachment in item (2) from being self-sufficient for a third party (a grader) to verify independently.

## The four things this closes

1. **A real CLI** (`src/cop/__main__.py`, `cli_peer.py`, `cli_replay.py`) — `peer` (zero required args, matching "role is fixed by which repo you are in, not a flag") and `replay --log <path>` (headless-first — a real grader's own situation is "just this log file, maybe no display").
2. **Nonce self-sufficiency** — `nonces_revealed` logged at the moment nonces stop being secret (rule 18: *until* game end, not forever), unconditionally, before the send is even attempted.
3. **The complete Table 20 bundle** — `report_game()` now attaches `declaration_`, `config_`, `log_`, and `result_` together, per email, per ch. 9.3.3's own "one end-of-game report" framing.
4. **A passive Step-0 wait** (`await_passive_step0`) — the CLI's non-initiating side needs a real way to learn "the peer already dialed in and negotiation is done" without polling or guessing.

## Milestone

Two real, independent `run_peer()` calls (one `initiate_step0=true`, one `false`), each loading its own config files from disk exactly as a real two-machine deployment would, reach a genuine negotiated, played, and reported (draft-mode) match end — through the CLI's own entry function, not a hand-assembled `Orchestrator(...)`. `uv run python -m cop replay --log <path>` against that match's real log file prints `Verified OK`. A tampered copy of the same log prints `TAMPERED` and exits `1`. A log with no Final Reveal (a crashed/incomplete match) prints a clear error and exits `1`, not a crash.

## Design questions answered here

**1. Does "initiator" for Step-0 also mean "goes first" in the match?** No — checked directly against `orchestrator_turn.py::take_turn` before designing anything: it computes and sends *this side's own* move independently each turn, informed by the peer's scent/hint via async callbacks, never blocking on the peer's own move to arrive. Both sides always call `play_game()` on themselves, unconditionally, regardless of `initiate_step0`. "Initiator" only ever decides who dials out first for the one-time Step-0 exchange.

**2. Why a passive-wait event instead of polling `self._opponent_repos is not None`?** Polling would work but reintroduces exactly the class of bug PRD 8's own retrospective already documents finding the hard way: naive synchronization across the responder's own server thread and the CLI's own asyncio loop. Reusing the identical `Event`/`call_soon_threadsafe` shape `orchestrator_capture.py` already established — set the loop *before* the wait, not after — was the first-draft answer here. **Corrected in this same layer, after `rule-auditor` reproduced a real gap the reuse alone didn't close** (Retrospective, below): the loop being set before the *wait* isn't the same as it being set before `_on_step0_received` can *fire at all* — `await_passive_step0` now checks `self._step0_completed` twice (before touching any state, and again right after the loop is set) so a negotiation that already resolved before this function was even called is recognized and returned/raised immediately, never silently discarded.

**3. Why does `_on_step0_received` set its own `PeerStateMachine(state="NEGOTIATING")` fresh, both when initiated *and* when passively awaited?** A genuine timeout on the passive side (nothing ever arrives) needs a legal `NEGOTIATING -> TECHNICAL_LOSS` edge available *before* any incoming call ever happens — `await_passive_step0` sets it itself, mirroring `negotiate_step0`'s own first line, but *only* once both completion checks (Design Question 2) have confirmed nothing resolved it first — otherwise `_on_step0_received`'s own already-correct final state (`WAITING_FOR_OPPONENT` or `TECHNICAL_LOSS`) is left untouched, never overwritten.

**4. Headless-by-default `replay`, GUI opt-in — not the other way around?** Rule 20 says "build a viewer application that replays and verifies" — nothing in the book ties that to a graphical window, and this repo's own actual grading situation (a log file handed to a script, possibly with no display at all) makes a text verdict the more robust default, matching how `check_config.py` (another spec-guard tool) already works. `--gui` still exists for a human who wants to look at it, via the already-built `ReplayViewerWindow` — reused, not reimplemented.

**5. Why does `run_peer()` accept `log_path`/`league_ledger_path` overrides when the CLI itself never exposes flags for them?** Found while writing this layer's own tests, not anticipated at design time: `Orchestrator.__init__`'s own defaults (`logs/trace.jsonl`, `LeagueLedger()`'s `logs/league_ledger.json`) are shared, single files — every test (and every real second sub-game run from the same machine) would otherwise collide on or silently overwrite the same file. `run_peer()` computes the real Table 20 log name (`logs/log_<game_id>_g<NN>.json`, via `report_bundle.log_filename` — reused, not reinvented) by default, and both are overridable so tests never touch the real repo's `logs/` directory.

**6. What about the missing `-m cop peer` CLI's own `--help` completeness — is `--tunnel` actually wired to `run_as_server`'s existing `use_tunnel` flag, or a new mechanism?** The former — `cli_peer.py::run_peer` passes `use_tunnel` straight through to `orchestrator.run_as_server(port=..., use_tunnel=use_tunnel)`, the same parameter `scripts/watch_prd5_tunnel.py` already exercises. No new tunnel logic; the CLI is a caller, not a reimplementation.

## Retrospective

Three real gaps surfaced after the first draft passed its own full test suite — two found by actually running the CLI as a human would, one found by `rule-auditor`'s own scoped pass (rules 6/7/18/20/34/49). All three fixed before this PRD's own commit, none left open.

**1. A doubled-suffix filename bug, found only by running `uv run python -m cop peer` as two real subprocesses and reading the actual files under `logs/` — not by any unit test.** `report_bundle.py::config_filename`/`log_filename` each append their own `_g{NN}` suffix from a separate `sub_game_number` parameter (`config_filename("dev", 1) == "config_dev_g01.json"`, per that function's own pre-existing test), but the first draft passed both the already-suffixed `game_id` string (`"dev-team_g01"`), producing `config_dev-team_g01_g01.json`. The one test checking attachment filenames passed anyway, because it computed its own expected value the same wrong way instead of checking `config_filename`/`log_filename`'s own contract.

**2. `declaration_`/`result_filename` were *also* wrong, in the opposite direction — found by `rule-auditor`, not by the fix above.** Closing gap 1 (switching `config_filename`/`log_filename` to the bare `group_id`) left `declaration_filename`/`result_filename` still receiving the compound `game_id`. `rule-auditor` checked this against `PARAMETERS.md`'s actual Table 20 text — *"File names derive from `game_id` and sub-game number `<NN>` so files from different games never mix"* — and against `report_bundle.py`'s own pre-existing (pre-PRD-10) test (`declaration_filename("dev") == "declaration_dev.json"`, no `<NN>`), confirming `declaration_`/`result_` are meant to take **only** the bare `game_id` — one evolving pair of files per series (`ResultBundle.sub_game_scores` is what accumulates per-sub-game data *inside* them), not a new pair per sub-game. Fixed by using the bare `game_id` for all four calls, with a separate `subject_id` (the compound, human-readable form) built just for the email subject line, which isn't part of Table 20's naming contract at all.

**3. A real, empirically-reproduced race in `await_passive_step0` — the most serious finding, and the reason PRD 8's own cross-thread pattern being *reused* wasn't automatically enough.** `orchestrator_capture.py`'s pattern is safe because the loop is captured immediately before the *outbound send that causally triggers the response* — nothing can arrive first. `await_passive_step0` has no such ordering: `_on_step0_received` is driven entirely by the peer's own independent timing, and `cli_peer.py`'s 0.5s `run_as_server` startup grace window is comfortably enough time for a real negotiation to complete — state already `WAITING_FOR_OPPONENT`, `_opponent_repos` already set — before `await_passive_step0` is ever called. The first draft unconditionally reset `state_machine` and waited anyway, discarding the real result and burning the full `step0_wait_seconds` (300s default) before raising a spurious `TECHNICAL_LOSS` on a match that had, in fact, already succeeded. `rule-auditor` reproduced this directly, not just by reading the code. Fixed with `self._step0_completed` (new `Orchestrator.__init__` state, set once by `_signal_step0_received`), checked twice in `await_passive_step0` — before touching any state, and again right after the loop is set, closing the gap between the two — with two new regression tests (`test_await_passive_step0_does_not_discard_a_negotiation_that_already_completed`, `..._relays_a_failure_that_already_completed`) that call `negotiate_step0` to completion *before* calling `await_passive_step0`, exactly reproducing the race.

**Smaller, same pass:** `league_ledger.py`'s own `ValueError` on a real rule-52 violation (`--counted` against an opponent already counted) reached `main()` uncaught, a raw traceback instead of the same clean `sys.exit(1)` path `Step0MismatchError` already gets — rule 52 itself was never bypassable (verified separately), this was purely a CLI robustness gap. Fixed with one more `except` clause and a regression test.

This is the third time in this project (after PRD 9's `repos`-validation gap and this PRD's own filename bug) that a real defect survived a full green test suite. Two of today's three were caught by two *different* techniques — literally running the CLI, and a scoped `rule-auditor` pass — neither of which would have caught what the other did: the filename bug was invisible to a design read (it only manifests in an actual filename on disk), and the race condition was invisible to every existing test because both `test_orchestrator_step0_wait.py`'s own `asyncio.gather` ordering and `test_cli_peer.py`'s single-process `asyncio.gather` both happened to make the passive side win the setup race by construction, every single time. Worth carrying forward as a standing argument for both techniques together, not either alone.
